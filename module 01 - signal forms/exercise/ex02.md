# Exercise 02 — Signal Forms: Contacts, Custom Rules & Submission

This exercise continues **directly from Exercise 01**. Start from your finished `claim-intake` application.

In Exercise 01 the clerk could fill in the basic claim details. Now the claim intake screen grows up:

- Descriptions must be meaningful — not just a word or two.
- The claim records **people**: the policy holder, the person reporting the claim, and any number of witnesses. All of them share the same validation rules.
- The form is actually **submitted** to a (fake) server — which may reject it.

You will practice:

1. **Custom validators** — field validators with `validate` and cross-field validators with `validateTree`
2. **Reusable schemas** — `schema`, `apply` and `applyEach`
3. **Submission** — `[formRoot]`, `submitting()`, and `onInvalid`
4. **Submission** — an `action` that returns server errors

### What you will add

| Field / Feature | Rules |
|---|---|
| **Description** | *(existing)* If filled — must contain at least **8 words** for `car` claims, **4 words** otherwise |
| **Policy Holder** | A contact: full name (required, at least 2 words), phone, email (valid format). **Phone or email** — at least one of them |
| **Reporter** | A contact — same rules |
| **Witnesses** | A list of contacts (add / remove) — same rules for each |
| **Submit** | Invalid form → focus the first invalid field. Valid form → send to server, all fields disabled while submitting |
| **Server rules** | Policy numbers starting with `X` are cancelled (error on the policy number field). The same policy cannot be submitted twice (error on the whole form) |

## Step 1 — A custom field validator: `minWords`

Built-in validators cover the basics, but business rules often need custom logic. The most basic tool is `validate(path, fn)`: the function receives a context and returns either `null` (valid) or an error object `{ kind, message }`.

### 1a. Try it inline

In your schema function, add:

```ts
import { validate } from '@angular/forms/signals';

validate(path.description, ctx => {
  const words = ctx.value().trim().split(/\s+/).length;
  return words < 8
    ? { kind: 'min-words', message: `At least 8 words please (currently ${words})` }
    : null;
});
```

✅ **Checkpoint:** Type a short description for a car claim, leave the field — the custom message appears (your error rendering from Exercise 01 already handles it — it's just another entry in `errors()`).

But try this: switch to a `home` claim and **clear** the description. The field is not required anymore… yet it is still invalid! 🤔

### 1b. Extract a reusable validator function

Create `src/app/validators/min-words.ts` and turn the rule into a function that looks and feels like the built-in validators:

```ts
import { LogicFn, SchemaPath, validate } from '@angular/forms/signals';

export function minWords(path: SchemaPath<string>, min: number | LogicFn<string, number>) {
  validate(path, ctx => {
    // TODO 1: if the (trimmed) value is empty, return null.
    //         Emptiness is the job of `required` — not ours.

    // TODO 2: resolve the threshold: `min` may be a number, or a function of ctx
    //         (just like `minLength(path, ctx => ...)` from Exercise 01).

    // TODO 3: count the words and return
    //         { kind: 'min-words', message: `Must contain at least ${threshold} words (currently ${count})` }
    //         or null.
  });
}
```

Replace the inline `validate(...)` with:

```ts
minWords(path.description, ctx => ctx.valueOf(path.type) === 'car' ? 8 : 4);
```

✅ **Checkpoint:**
- Car claim, 3 words → *"Must contain at least 8 words (currently 3)"*. Switch to `travel` → *"…at least 4 words…"*.
- `home` claim with an empty description → valid. 
- Empty description on a `car` claim → only *"A description is required for car claims"* (from `required`), not two errors.

> **Rule of thumb:** a custom validator should ignore empty values and let `required` decide whether empty is OK. That's what makes validators composable.

## Step 3 — A reusable schema with a cross-field validator

All contacts share the same rules. Instead of writing them three times (and once per witness!), define them **once** as a standalone schema.

Create `src/app/validators/contact.schema.ts`:

```ts
import { email, required, schema, validateTree } from '@angular/forms/signals';
import { Contact } from '../models/claim.model';
import { minWords } from './min-words';

export const contactSchema = schema<Contact>(path => {
  // inside here, `path` is a Contact — not a Claim!
});
```

Inside the schema add:

1. `required` on `fullName` with a message.
2. `minWords(path.fullName, 2)` — a full name is a first **and** last name. (See how your custom validator from Step 1 is already paying off.)
3. `email(path.email, { message: ... })` — another built-in validator. Like your `minWords`, it ignores empty values.
4. **Phone or email** — this rule involves *two* fields. `validate` can only return errors for the field it's attached to, so use `validateTree` on the whole contact. It may return a list of errors, each one targeted at a specific field via `fieldTree`:

   ```ts
   validateTree(path, ctx => {
     const noPhone = ctx.valueOf(path.phone).trim() === '';
     const noEmail = ctx.valueOf(path.email).trim() === '';
     if (noPhone && noEmail) {
       return [
         { kind: 'no-contact-method', message: 'Provide a phone or an email', fieldTree: ctx.fieldTreeOf(path.phone) },
         // TODO: the same error, targeted at the email field
       ];
     }
     return null;
   });
   ```

> **`validate` vs `validateTree`:** `validate` reports errors on its own field. `validateTree` is attached to a parent and can report errors on any of its descendants — perfect for cross-field rules.

## Step 4 — `apply` the schema to the policy holder and the reporter

In the main form's schema function (in `app.ts`):

```ts
import { apply } from '@angular/forms/signals';

apply(path.policyHolder, contactSchema);
apply(path.reporter, contactSchema);
```

That's it — two lines, all the rules.

### Render the contacts

The markup for a contact is also identical each time, so let's make a small component for it. Create `src/app/contact-fields/contact-fields.ts`:

```ts
import { Component, input } from '@angular/core';
import { FieldTree, FormField } from '@angular/forms/signals';
import { Contact } from '../models/claim.model';

@Component({
  selector: 'app-contact-fields',
  imports: [FormField],
  templateUrl: './contact-fields.html',
})
export class ContactFields {
  readonly contact = input.required<FieldTree<Contact>>();
}
```

In `contact-fields.html`, write the three fields (`fullName`, `phone` as `type="tel"`, `email` as `type="email"`) exactly as you did in Exercise 01 — label, required hint, input, errors — but bound to `contact().fullName`, `contact().phone`, etc.

Use it in `app.html` (and add `ContactFields` to the `imports` of `App`):

```html
<fieldset>
  <legend>Policy Holder</legend>
  <app-contact-fields [contact]="claimForm.policyHolder" />
</fieldset>
<!-- ... and the same for the reporter -->
```

> Notice the nice symmetry: a **reusable schema** for the rules + a **reusable component** that takes a `FieldTree<Contact>` for the UI. Neither of them knows anything about claims.

✅ **Checkpoint:**
- Both fieldsets show `Full Name *`.
- Type `Dana` as the holder's name → *"Must contain at least 2 words (currently 1)"*.
- Leave phone and email empty → both show *"Provide a phone or an email"*. Fill in **either** one → both errors disappear.
- `not-an-email` in the email → format error.
- Each contact is validated independently: fixing the holder does not affect the reporter.

## Step 5 — `applyEach` for the witnesses list

`apply` attaches a schema to one object. `applyEach` attaches it to **every item** of an array — including items added later:

```ts
applyEach(path.witnesses, contactSchema);
```

### Add / remove witnesses

The model is immutable, so adding or removing a witness means writing a **new** claim into the signal. Add to `App`:

```ts
addWitness() {
  this.data.update(claim => ({ ...claim, witnesses: [...claim.witnesses, EMPTY_CONTACT] }));
}

removeWitness(index: number) {
  // TODO: same idea — use filter() to build a new array without the item at `index`
}
```

### Render the list

A `FieldTree` of an array is **iterable** — each item is itself a `FieldTree<Contact>`, ready to be passed to your component:

```html
@for (witness of claimForm.witnesses; track $index) {
  <fieldset>
    <legend>Witness #{{ $index + 1 }}</legend>
    <app-contact-fields [contact]="witness" />
    <button type="button" (click)="removeWitness($index)">Remove witness</button>
  </fieldset>
}
<button type="button" (click)="addWitness()">+ Add witness</button>
```

> Why `type="button"`? In the next step this markup will live inside a `<form>`, where a plain `<button>` defaults to `type="submit"`.

✅ **Checkpoint:**
- Add two witnesses → each one gets its own validation (required name, phone-or-email, …).
- Remove the first witness → the second one moves up, keeping its values **and** its errors.
- The JSON panel shows the `witnesses` array growing and shrinking.

## Step 6 — Submission: `formRoot` and `onInvalid`

Until now the form has never been submitted. Let's change that.

### 6a. Turn the container into a real form

1. In `app.html`, replace the outer `<div class="form">` with:

   ```html
   <form class="form" [formRoot]="claimForm">
     ...
   </form>
   ```

2. Add `FormRoot` (from `@angular/forms/signals`) to the component `imports`.
3. Add a submit button at the end of the form:

   ```html
   <button type="submit">Submit Claim</button>
   ```

### 6b. Configure the submission

`form()` accepts a **third** argument — options. The `submission` option tells the form what to do on submit:

```ts
readonly claimForm = form(this.data, path => {
  // ... all your rules ...
}, {
  submission: {
    action: async field => {
      console.log('Submitting', field().value());
      return null; // null = success, no errors
    },
    onInvalid: field => {
      // TODO
    },
  },
});
```

When the user submits, the form:
1. Marks **all** fields as touched — so every error becomes visible at once.
2. If the form is valid → runs `action`.
3. If it is invalid → runs `onInvalid` instead.

### 6c. Implement `onInvalid`

A long form with an error somewhere at the bottom is frustrating. In `onInvalid`, focus the first invalid field:

- `field().errorSummary()` returns **all** errors of the form and its descendants. Each error has a `fieldTree` telling you where it lives.
- A field's state has a `focusBoundControl()` method that focuses the control bound to it with `[formField]`.

Put these two together (careful — the list may be empty).

✅ **Checkpoint:**
- Reload, click **Submit Claim** on the empty form → all errors appear (including inside the contacts), and the cursor jumps to *Policy Number*.
- Fill the top fields correctly and submit again → focus jumps to the policy holder's *Full Name*.
- Fill everything correctly → submit → the console shows `Submitting` with the whole claim.

## Step 7 — Submission: an async `action` that returns errors

Some rules can only be checked by the server. Let's simulate one.

### 7a. A fake server

Create `src/app/services/claims-api.ts`:

```ts
import { Injectable } from '@angular/core';
import { Claim } from '../models/claim.model';

export type SubmitResult =
  | { ok: true; claimId: string }
  | { ok: false; reason: 'policy-cancelled' | 'duplicate-claim' };

@Injectable({ providedIn: 'root' })
export class ClaimsApi {
  private readonly submittedPolicies = new Set<string>();

  async submit(claim: Claim): Promise<SubmitResult> {
    await new Promise(resolve => setTimeout(resolve, 2000));

    if (claim.policyNumber.toUpperCase().startsWith('X')) {
      return { ok: false, reason: 'policy-cancelled' };
    }
    if (this.submittedPolicies.has(claim.policyNumber)) {
      return { ok: false, reason: 'duplicate-claim' };
    }

    this.submittedPolicies.add(claim.policyNumber);
    return { ok: true, claimId: `CLM-${Math.floor(Math.random() * 100_000)}` };
  }
}
```

### 7b. Call it from the action

Inject `ClaimsApi` into `App`, and add a `lastClaimId = signal<string | null>(null)` to show a success message.

The `action` returns its result as **validation errors** — exactly the same shape as `validateTree` errors:

- `null` (or an empty array) → success.
- An error **with** a `fieldTree` → it is attached to that field.
- An error **without** a `fieldTree` → it is attached to the form itself.

Implement the action:

1. Clear `lastClaimId`.
2. `await` the API with `field().value()`.
3. On success → set `lastClaimId` and return `null`.
4. On `policy-cancelled` → return `{ kind: 'policy-cancelled', message: 'This policy was cancelled', fieldTree: field.policyNumber }`.
5. On `duplicate-claim` → return a similar error **without** `fieldTree`.

### 7c. Show the result

At the top of the form, show the form-level errors and the success message:

```html
@for (err of claimForm().errors(); track err.kind) {
  <div class="form-error">{{ err.message }}</div>
}
@if (lastClaimId(); as id) {
  <div class="form-success">Claim {{ id }} was submitted successfully</div>
}
```

Field-level server errors need no extra work — they are part of the field's `errors()`, which you already render.

### 7d. While submitting…

Two seconds is a long time. Let the user know, and prevent edits:

1. In the button, use the form's `submitting()` state:

   ```html
   <button type="submit">
     @if (claimForm().submitting()) { Submitting... } @else { Submit Claim }
   </button>
   ```

2. Disable the **whole form** during submission with a single rule on the root path:

   ```ts
   disabled(path, { when: ctx => ctx.state.submitting() });
   ```

   (`ctx.state` is the state of the field the rule is attached to — here, the root.) Disabling a parent disables all its descendants.

✅ **Checkpoint:**
- Submit a valid claim → button shows *Submitting...*, all inputs are greyed out, then *"Claim CLM-… was submitted successfully"*.
- Submit again without changes → *"A claim for this policy was already submitted"* at the top.
- Change **any** field → the form-level error disappears by itself.
- Set the policy number to `X1234567` and submit → *"This policy was cancelled"* under the policy number field. Edit the policy number → the error disappears.

> **Why do server errors disappear on edit?** Submission errors are tied to the value they were reported for. Once the value of the field changes, they are cleared automatically — the server hasn't seen the new value yet.
